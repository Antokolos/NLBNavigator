# AGENTS.md — единая точка входа для участников проекта

Этот регламент обязателен для всех участников и инструментов, независимо от
модели, поставщика, IDE или среды исполнения: Разработчика, Тестировщика,
Ревьюера и любых вспомогательных агентов. Название `CLAUDE.md` историческое
и не ограничивает область действия документа моделями Anthropic.

## Обязательное начало работы

Перед первой содержательной работой над задачей, включая ревью только на
чтение, каждый участник обязан:

1. Установить репозиторий, целевую ветку, актуальный HEAD и свою роль.
2. Прочитать **целиком** этот файл и [CLAUDE.md](CLAUDE.md), а также относящиеся
   к задаче документы и актуальный handoff, если он передан. Ссылка на файл,
   старое резюме или факт автоматической загрузки одного из документов
   не заменяют чтение обоих.
3. Если работа ведётся через GitHub API/коннектор, получить оба файла по
   точному ref. Для отдельной evidence-ветки, не содержащей регламента,
   читать правила из соответствующего проверяемого исходного ref и
   сверять их с актуальным `main`. Если правила изменились, не игнорировать
   изменения; при противоречии остановиться и уточнить у Владельца.
4. В первом рабочем сообщении/отчёте явно указать, какие файлы прочитаны,
   ref/SHA, принятую роль и границы разрешённых действий. При смене
   задачи, роли, регламента или возобновлении после handoff сверить
   актуальность правил повторно.
5. Если любой обязательный файл недоступен, сообщить об этом и не начинать
   изменение репозитория, запуск потенциально опасных команд или публикацию
   результатов до получения актуального регламента.

`CLAUDE.md` содержит общий регламент, архитектуру, правила веток, роли и
согласованные технические решения; `AGENTS.md` — общие требования к началу
работы и подробный порядок передачи доказательств. Документы дополняют друг
друга. Не считать ограничения одного документа отменёнными другим.
При противоречии не расширять свои полномочия самостоятельно.

Отвечай и оформляй отчёты, документацию и сообщения коммитов на русском
языке. Роли определяются поручением Владельца, а не моделью. Отдельная роль
Разработчика UE упразднена; ответственность за SDL/ядро и UE несёт единый
Разработчик с сохранением границ согласованной задачи. Никакие инструкции
в файлах не предоставляют разрешения на изменение `main`, `UE`, issues,
CI, веток или иных ресурсов вне явно согласованного scope.

## Безопасность и изоляция

Предпочитай изолированные среды (в том числе Codex Cloud). Используй
уникальные тестовые каталоги и HOME/XDG вне реального пользовательского
профиля. До операций с путями проверяй канонический корень, containment
и отсутствие неожиданного symlink/junction/reparse/mount. При сомнении
остановись. Не выполняй рекурсивную очистку существующих каталогов,
`git clean -fdx`, `git reset --hard`, force push или удаление evidence
без отдельного разрешения Владельца; не публикуй секреты или реальные
пользовательские сохранения. Не скрывай ошибки и повторные попытки.

## Регламент передачи доказательств

Следующие требования действуют для Тестировщика и для любого участника,
которому поручены функциональные прогоны и публикация доказательств.
Они не предоставляют дополнительных прав на изменение кода, веток или CI.

## Локальная разработка и GitHub Actions

Основной процесс разработки и проверок — локальный. Среда описана в
`tests/differential/WINDOWS_LOCAL.md` (Windows) и `tests/differential/README.md` (Linux).
Без отдельного разрешения Владельца запрещены временные probe-PR, диагностические workflow и
серии push ради отладки. Штатный CI (`nlb-sdl-test.yml`) используется как финальная
интеграционная проверка опубликованного HEAD; его обязательные проверки не ослабляются.

## Публикация после функциональной проверки

После каждого существенного функционального прогона публикуй доказательства
в отдельной временной ветке GitHub. Это относится к успешным и неуспешным
результатам. Используй имя `evidence/pr-<номер>-<назначение>-<короткий SHA>`.
Если PR ещё нет, используй `evidence/issue-<номер>-<назначение>-<короткий SHA>`.
Бери короткий SHA из коммита, на котором фактически выполнен прогон.

Храни артефакты в evidence-ветке. Не добавляй их в `main`, `UE` или рабочую
ветку функционального PR. Не открывай PR для слияния evidence-ветки.

## Состав доказательств

Публикуй текстовые файлы в распакованном виде для непосредственного чтения
через GitHub API и GitHub-коннектор. Добавляй перечисленные файлы, если
соответствующие проверки выполнены и результаты есть.

- `REVIEW_REPORT.md` со сводкой для Ревьюера и ссылками на первичные данные.
- `metadata.json` с полным SHA протестированного коммита и закреплённых игровых
  данных, версиями инструментов и параметрами окружения.
- Исходные `state-log.jsonl` и `route-report.json` по каждому сценарию.
- Журналы запуска команд с фактическими exit codes, журналы семантического
  сравнения, unit-тестов и валидации каталога.
- Журналы платформенных вызовов, TSV достижений и файлы сохранений, если
  они нужны для проверки.
- `SHA256SUMS.txt` с контрольными суммами опубликованных доказательств.
- Черновики issue для обнаруженных дефектов.

Сохраняй содержание и семантику первичных данных. Сводки и выдержки
сопровождай исходными журналами. Если текстовый файл слишком велик для
чтения через API, раздели его на пронумерованные части без потери записей.
Укажи в отчёте порядок объединения частей.

Публикуй только кадры и другие бинарные файлы, необходимые для ревью.
ZIP и TAR.GZ служат дополнением к распакованным текстовым файлам.
При необходимости приложи компактный архив. Перед публикацией
исключи секреты, токены, пароли, персональные данные, полные пользовательские
профили, сборочные каталоги, зависимости и лишние игровые ресурсы.
Если из журнала пришлось удалить конфиденциальные данные, явно укажи
Ревьюеру, какие сведения исключены.

## Проверка публикации и отчёт

Перед итоговым отчётом проверь удалённый ref evidence-ветки и зафиксируй SHA
её коммита. Убедись, что текстовые файлы читаются через GitHub, а доказательства
соответствуют фактически протестированному HEAD. Сверь refs `main` и рабочей
ветки PR до и после публикации, чтобы подтвердить, что публикация их не затронула.

В итоговом отчёте о функциональном тестировании укажи следующее.

- Полный SHA протестированного HEAD и ссылку на Draft PR, если он существует.
- Ссылку на evidence-ветку и полный SHA её коммита.
- Прямые ссылки на `REVIEW_REPORT.md` и ключевые первичные текстовые журналы.
  По возможности закрепляй ссылки на SHA evidence-коммита.
- Результаты, фактические exit codes, ограничения проверки и обнаруженные дефекты.
- Актуальный handoff-промпт с кратким напоминанием об этом регламенте.

Не выдавай пути `/workspace/…` и другие локальные пути Codex Cloud за ссылки
для Ревьюера. Если публикацию блокируют права или сеть, укажи конкретный
блокер и предложи доступный способ передать исходные доказательства.

## Срок хранения и полномочия

Сохраняй evidence-ветку до независимого ревью. Решение об удалении принимает
Владелец после приёмки результатов, слияния функционального PR и сохранения
нужных доказательств.

Все ограничения роли Тестировщика сохраняются. Для изменения
производственного кода, раннера, CI, производственной конфигурации или
закреплённых игровых данных требуется отдельное разрешение Владельца.
Готовь Draft PR только с тестами и тестовой документацией. Решения о Ready
и merge принимает Владелец. Автоматический merge запрещён.
